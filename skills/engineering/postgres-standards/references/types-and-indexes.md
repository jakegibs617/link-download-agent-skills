# Types and Indexes

Selection tables for the two decisions that are cheap at design time and expensive
afterwards. Each row names the failure the wrong choice causes, because "prefer X" without
a consequence does not survive contact with an opinionated reviewer.

> Version gates are stated by major version; confirm against the release notes for the exact
> server version in use.

## Type selection

| Instead of | Use | Failure the wrong choice causes |
|---|---|---|
| `varchar(255)` | `text`, or `varchar(n)` with a real business limit, or a `CHECK (length(col) <= n)` | Postgres stores both identically and `varchar(n)` costs a length check, not space. 255 is a MySQL row-format artifact. Widening later is free; the arbitrary limit is what breaks — an email address, a URL, a name in a script with combining characters. |
| `char(n)` | `text` | Blank-padded to `n` on every read, and comparison semantics differ from `text`. There is no performance upside. |
| `timestamp` (without time zone) | `timestamptz` | Silently interprets input in the session `TimeZone` and stores no offset. Two servers with different `TimeZone` settings write different instants for the same input. This is the single most common irreversible data defect in a Postgres schema. |
| `time with time zone` | `time` plus a date, or `timestamptz` | The type is meaningless without a date — offsets depend on DST. |
| `float4` / `float8` / `real` for money | `numeric(12,2)` (or integer minor units) | Binary floating point cannot represent 0.10; sums drift and reconciliation fails. |
| `money` | `numeric` | Locale-dependent output, fixed fractional precision from a server setting, no useful arithmetic guarantees. |
| `serial` / `bigserial` | `GENERATED ALWAYS AS IDENTITY` (**PG 10+**) | `serial` is a macro creating a sequence with fragile ownership: it survives `ALTER TABLE`, breaks on table copies, permits explicit inserts that desynchronise the sequence, and its grants are separate. Identity columns are the SQL-standard equivalent that the catalog understands. |
| `int4` primary key on a growing table | `bigint` | 2.1 billion arrives faster than expected and the fix is a full table rewrite under `ACCESS EXCLUSIVE`. `bigint` costs four bytes. |
| Random UUID (`v4`) primary key | `bigint` identity, or time-ordered UUID v7 (`uuidv7()` **PG 18+**; extension or app-side generator before that) | Random keys scatter B-tree inserts across every leaf page, destroying cache locality and inflating WAL and index bloat. Measurable from roughly ten million rows. Use v4 only when keys must be generated by untrusted clients or merged across systems — and say so. |
| `uuid` stored as `text` | `uuid` | 37 bytes vs 16, no validation, and comparisons go through collation. |
| `enum` type | Lookup table with an FK, unless the set is genuinely fixed | Adding a value is fine (`ALTER TYPE ... ADD VALUE`, **PG 12+** works inside a transaction block), but removing or reordering one requires recreating the type and every column using it. Lookup tables also carry labels, ordering, and soft-deprecation. |
| `jsonb` for known attributes | Real columns | No constraints, no statistics worth planning on, no FK, and every read pays parse cost. Use `jsonb` for genuinely open-ended or third-party payloads. Never `json` — it stores raw text and reparses on every access; `jsonb` is the operational type. |
| `text` with `lower()` everywhere | `citext` extension, or a nondeterministic ICU collation (**PG 12+**) | Every call site has to remember, and one that forgets both returns wrong results and misses the index. |
| Nullable boolean as a flag | `boolean NOT NULL DEFAULT false`, or three explicit states | Three-valued logic leaks into every predicate: `WHERE NOT flag` silently excludes NULL rows. |
| A column derived from other columns, maintained by a trigger | `GENERATED ALWAYS AS (...) STORED` (**PG 12+**) | Triggers drift, are skipped by bulk loads, and are invisible in the schema. |
| Array column as a many-to-many | Junction table | No referential integrity, no efficient join, and updates rewrite the whole array. Arrays are fine for small fixed-cardinality tag sets that are only ever read whole. |
| `timestamptz` range in two columns | `tstzrange` + `EXCLUDE USING gist` | Overlap prevention in the application is a race condition; an exclusion constraint is not. |

**Column order matters slightly:** Postgres aligns fixed-width types, so ordering columns
widest-first reduces per-row padding. Worth doing on very wide, very large tables; not worth
arguing about elsewhere.

## Index selection

| Situation | Index | Notes |
|---|---|---|
| Equality and range on a scalar; sorting; `LIKE 'prefix%'` in the C collation | **B-tree** (default) | Covers `=`, `<`, `>`, `BETWEEN`, `IN`, `ORDER BY`, and `IS NULL`. **PG 13+** deduplicates repeated keys, shrinking low-cardinality indexes substantially. |
| Containment in `jsonb`, arrays, or full-text search | **GIN** | `jsonb_ops` (default) supports key-exists operators; `jsonb_path_ops` is smaller and faster but only supports `@>`. Slower to update — batch writes benefit from a larger `gin_pending_list_limit`. |
| Geometric, range-overlap, nearest-neighbour, exclusion constraints | **GiST** | The only index that backs `EXCLUDE` constraints. |
| Very large, naturally clustered append-only data (time series) | **BRIN** | Tiny — kilobytes where B-tree would be gigabytes. Only useful when physical row order correlates with the column, which is exactly the append-only case. Useless after random updates. |
| Simple equality on a very wide column, no ordering needed | **Hash** | Crash-safe and replicated from **PG 10+**. Rarely beats B-tree enough to justify losing range support. |
| Predicate matches a small slice of the table | **Partial** — `CREATE INDEX ... WHERE deleted_at IS NULL` | Often an order of magnitude smaller. The query's `WHERE` clause must imply the index predicate for the planner to use it. |
| Query filters on an expression | **Expression** — `CREATE INDEX ON users (lower(email))` | The query must use the identical expression. Also fixes the `lower()` pattern above without `citext`. |
| Index-only scans on a query that also selects a non-key column | `INCLUDE (...)` covering index (**PG 11+**) | Payload columns are stored in leaf pages only, so they do not affect uniqueness or ordering. Index-only scans still require a well-vacuumed visibility map. |

### Composite index rules

- Column order follows the query: equality predicates first, then the range predicate, then
  the `ORDER BY` columns. A composite on `(a, b)` serves `WHERE a = ?` and
  `WHERE a = ? AND b = ?`, but not `WHERE b = ?`.
- A composite on `(a, b)` makes a separate index on `(a)` redundant. Drop it — every index
  taxes every write and consumes cache.
- Declare `DESC` / `NULLS FIRST` in the index when the query's `ORDER BY` does, or the
  planner adds a sort anyway.

### Every index costs

Each index is written on every `INSERT` and on every `UPDATE` that touches its columns —
and an update to an indexed column forfeits the HOT-update optimisation, meaning a new index
entry in every index on the table. On a hot-write table, state that cost explicitly before
adding one. Indexes that are never scanned are pure tax: see the `idx_scan` detection query
in [antipatterns.md](antipatterns.md).
